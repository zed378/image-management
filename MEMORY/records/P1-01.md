## What was built

Three migrations (`packages/db/src/migrations/20260921T15{00,10,20}_*`), 18
new tables, all registered statically:

- **Assets** -- `folders`, `assets`, `asset_versions`, `asset_metadata`,
  `image_derivatives`, `tags`, `asset_tags`, `collections`,
  `collection_assets`.
- **Access** -- `role_assignments`, `api_keys`, `api_key_projects`; plus
  composite-FK targets `users (id, tenant_id)` and
  `projects (id, application_id, tenant_id)`.
- **Platform** -- `webhooks`, `webhook_deliveries`, `usage`, `quotas`,
  `quota_overrides`, `audit_logs` (with the append-only guard trigger).

`packages/db/src/types.ts` has a row type for every table.
`packages/db/src/connection.ts` now parses `date` as a `YYYY-MM-DD` string.

## Definition of Done evidence

- **Every DATABASE document is Final and matches the schema exactly** -- and
  this is checked, not asserted: each document embeds generated
  column/constraint/index blocks (`packages/test-utils/src/schema-doc.ts`,
  rendered from `pg_catalog`), and `schema-docs.int.test.ts` fails CI when a
  document drifts. Regenerate with `UPDATE_SCHEMA_DOCS=1`.
- **Migration lint** -- `data-model.int.test.ts` holds a scope for every
  table (`global` / `tenant` / `project`) and fails on an unclassified
  table, a tenant-owned table without `NOT NULL tenant_id`, a project-owned
  one without `NOT NULL project_id`, any FK into tenant data that does not
  carry `tenant_id`, any FK between project-owned rows that does not carry
  `project_id`, and any Postgres enum type. Global tables: `tenants`,
  `quotas` (documented in `docs/DATABASE/00`).
- 18 behavior tests prove the integrity rules are enforced by the database:
  cross-project folder/tag links, a current-version pointer at another
  asset's version, a key naming another application's project, ready
  versions without facts, visibility outside the five levels, case-
  insensitive tag/folder uniqueness, collection purge restriction,
  derivative identity, audit UPDATE/DELETE/TRUNCATE refused and the purge
  path confined to its own transaction.
- Rollback: every migration reverts in reverse order to an empty schema and
  re-applies (new test).

## Decisions

`ADR-022` resolves what the specification left open or contradicted: table
names; same-project integrity as composite FKs over `(id, project_id,
tenant_id)`; API keys and webhooks per application; HMAC-SHA256+pepper key
hash; asset status and soft-delete; visibility on the asset with five
levels; bytes-derived facts on versions; version id in object keys;
derivative identity column order; idempotency as its own table (`P2-02`);
usage daily buckets and quota overrides; append-only audit in the
database; encrypted webhook secrets.

Documents corrected in the same change: `TASKS/PHASE-1` (P1-01 table list,
P1-02 hashing), `TASKS/PHASE-2` (P2-08 deletion marker),
`docs/ENGINEERING/07` (table map, the two load-bearing unique indexes),
`docs/ENGINEERING/01` (derivative index column order).

## Deviations from the spec

- `docs/DATABASE/18` retention durations are engineering defaults, each a
  config key; per-plan values wait on `docs/PLAN/16`/`17` (business input).
  Its acceptance box for that is left unchecked on purpose.
- No `api_key_projects` / `quota_overrides` were named by the task; both are
  needed to express the specified rules as constraints (ADR-022).

## Bugs found and fixed

1. **`pg` turns a `date` into a JS `Date` at local midnight**, so a usage day
   read on a server east or west of UTC would shift by the offset. Parsed as
   a string now; tested.
2. **The schema-doc checker passed on an empty marker block** (my first
   version's regex required a line between the markers, so a new, empty
   block was never filled and the comparison compared nothing). Regex fixed
   and a guard added: every marker must come out holding a generated table.
