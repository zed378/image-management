## What was built

- Step 1 (tables): `usage`, `quotas`, `quota_overrides` were created in
  `P1-01`. Added `usage_event_ledger` (migration `20260921T1610`) for
  exactly-once application; classified in the migration lint, the scope
  map, and the generated schema docs.
- `packages/queue` -- the job-queue interface with BullMQ
  (`createBullQueue`, `createBullWorker`, explicit `DEFAULT_JOB_OPTIONS`)
  and an in-memory implementation for unit tests; the usage job contract
  (`USAGE_QUEUE`, `RECORD_USAGE_JOB`, `usageEventSchema` -- counters only).
- Producer: `services/api/src/modules/usage/usage-recorder.ts` batches counts
  per (project, metric, UTC day) in memory and enqueues one job per bucket
  per flush (60 s), keeping counts on enqueue failure.
- Consumer (step 2): `services/worker/src/modules/usage/` -- the aggregator
  parses the job, claims the event id in the ledger and increments the
  counter in one transaction, both through `scoped()`. The worker server now
  runs this consumer with graceful shutdown (`WORKER_USAGE_CONCURRENCY`,
  default 4).
- Step 3: no enforcement. `docs/PLAN/15` is Final.

## Definition of Done evidence

- `docs/PLAN/15-QUOTA-LIMITS.md` defines every metric (unit, counter or
  gauge, source, period), the scope (recorded per project/day, limited per
  tenant) and the over-limit behavior for each (hard 429, hard-degrade for
  delivery, soft notify). The per-plan numbers are business input (PLAN/17)
  and stored as data -- its acceptance box is left unchecked on purpose.
- Tests: exactly-once under redelivery and under four concurrent deliveries
  of one event; batches of a bucket add up; malformed or gauge events are
  rejected; a project from another tenant is refused by the composite FK;
  an event enqueued through real BullMQ/Redis lands in `usage`. The built
  `dist/server.js` of the worker started against compose and reported its
  queue.
