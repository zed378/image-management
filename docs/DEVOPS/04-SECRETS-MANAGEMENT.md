# 04 - Secrets Management

> Category: **DevOps** (`docs/DEVOPS/`) &nbsp;|&nbsp; Status: Final (v1) &nbsp;|&nbsp; Owner: TBD

## Purpose

Where secrets live, how they reach a process, and how they are kept out of
places they must never be.

## Category Mandate

Environments, containerization, CI/CD, configuration and secrets management,
migrations, backup/restore, and disaster recovery.

---

## What counts as a secret

| Secret | Variable | Rotation |
|---|---|---|
| Database password | inside `DATABASE_URL` | on compromise, and on staff change |
| Redis password | inside `REDIS_URL` (when set) | as above |
| Storage credentials | `STORAGE_S3_ACCESS_KEY_ID` / `STORAGE_S3_SECRET_ACCESS_KEY` | 90 days, or use an IAM role and have none |
| API-key pepper | added by `P1-02` | rare; changes every stored key hash |
| Signed-URL secrets | per application, in the database (`P5-02`) | per application, self-service |
| Webhook signing secrets | per endpoint, in the database (`P6-03`) | per endpoint, self-service |

The last two are tenant data, not deployment configuration: they are
generated by the platform, stored encrypted in the database, and rotated
through the API. The rest are deployment secrets and follow this document.

## Where deployment secrets live

**AWS Secrets Manager**, injected into the process as environment variables
by the orchestrator at start time.

The platform's contract with the secrets manager is deliberately narrow:
*a secret arrives as an environment variable before the process starts*. No
code calls a secrets-manager SDK. Consequently switching to Vault, Doppler,
GCP Secret Manager, or a Kubernetes `Secret` changes the deployment manifest
and nothing in the code -- the same property `ADR-001` gives storage.

AWS Secrets Manager is chosen because S3 is the v1 production storage
baseline (`ADR-002`), so the platform is expected to run in AWS, and an IAM
role can then both read the secrets and grant S3 access without a static
storage key at all.

## Rules

1. **Never in the repository.** Not in code, not in a default value, not in
   a test fixture that looks real. `.env.example` holds local-only
   credentials for the local compose stack; they are public by construction
   and must never be reused anywhere shared.
2. **Never baked into an image.** Configuration, including secrets, is
   injected at runtime (`03-CONFIGURATION.md`).
3. **Never in a log, an error message, or a response body.**
   `ConfigError` names variables and never values (`packages/config`); the
   logger's redaction list (`P0-05`, `docs/ENGINEERING/12`) removes secret
   fields from every log line.
4. **No defaults.** A missing secret fails startup.
5. **A leaked secret is rotated first, cleaned up second.** Git history keeps
   what a revert removes; assume anything committed is compromised.
6. **Least privilege.** The `api` and `worker` roles get the S3 actions they
   use on their own bucket and nothing more; the database role cannot
   `UPDATE` or `DELETE` audit rows (`P1-07`).

## Local development

`cp .env.example .env`. The values match `deploy/docker-compose.yml` and are
only valid against that local stack.

## Detection

Secret scanning runs in CI (`P0-10`). A finding blocks the merge; the fix is
rotation, not just deletion.

## Acceptance Criteria

- [x] Every deployment secret is named, with where it lives and how it rotates.
- [x] The secrets manager is named, and the code's contract with it is stated
      so that changing providers is a manifest change.
- [x] The never-log rule is backed by a mechanism (`ConfigError`, the logger
      redaction list) rather than by convention.
