## What was built

- `services/api/src/modules/audit/audit.ts` -- `AUDIT_ACTIONS` (closed
  vocabulary) and `audited(db, ctx, work)`: the work runs in a transaction
  and must *return* its audit entries, which are inserted (through
  `scoped()`) in that transaction. Entries carry actor, action, target,
  application/project, request id, client address, metadata.
- API-key create/rotate/revoke and tenant provisioning now go through
  `audited`. Revoke became idempotent-aware (`repository.revoke` returns
  whether it changed anything), so a repeated revoke records nothing.
- `TenantContext.sourceIp` (from `request.ip`, after trusted proxies).
- Migration `20260921T1600_create_app_role`: the `image_delivery_app` group
  role with table privileges and default privileges for later tables, but
  only SELECT/INSERT on `audit_logs` and nothing on the migrator's tables.
- Docs: `SECURITY/17` Final; `DEVOPS/04` "Database roles".

## Definition of Done evidence

- **Audit rows are provably immutable** -- `services/api/tests/audit.int.test.ts`
  creates a login role in `image_delivery_app`, connects as it, and asserts
  UPDATE, DELETE and TRUNCATE on `audit_logs` fail with `permission denied`
  while INSERT/SELECT and ordinary writes on other tables work. The trigger
  guard (P1-01) independently refuses the same for any role.
- Step 2 ("cannot be bypassed"): tests show a failing change writes no
  entry and a failing entry undoes the change.

## Deviations / follow-ups

- Actions for features that do not exist yet (visibility, purge, roles,
  admin) are in the vocabulary and listed in `SECURITY/17` with the task
  that will write them.
- Local development and tests still connect as the schema owner; the
  production split (a login role in `image_delivery_app`) is documented in
  `DEVOPS/04`.
- An audit-log read API (`audit-log:read`) belongs with the dashboard
  (`P6-11`).
