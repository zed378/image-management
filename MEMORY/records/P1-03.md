## What was built

- `services/api/src/http/authentication.ts` -- registered first inside the
  `/v1` scope:
  - `onRoute`: every route must declare `config.permission` or
    `config.public: true`, else registration throws (SEC-AZ-01);
  - `onRequest` (before the body is read): failure-limiter check, `Bearer`
    parsing, `apiKeys.authenticate`, `request.tenant` built from the
    principal only, request log bound to `tenant_id`/`key_id`;
  - `preHandler`: the route's permission, else `403 permission_denied`.
  401s carry `WWW-Authenticate: Bearer realm="api"`; a credential-store
  failure is `503 service_unavailable`, never `401`.
- `services/api/src/http/failure-limiter.ts` -- 20 failures / 60 s / per
  address, bounded to 10,000 addresses, in memory (floor until `P5-03`).
- `services/api/src/modules/api-keys/api-key.routes.ts` -- the five
  key-management routes (`api-key:create|read|update|delete`).
- The API-key service gained two rules: **application scope** (a key
  manages only its own application's keys; another id is `404
  application_not_found`) and **no escalation** (a caller can issue or
  rotate only a key within its own permissions and project coverage).
- `server.ts` wires the service, the last-used tracker (started, flushed on
  shutdown) and the routes. `app.ts` takes `apiKeys`, an optional
  `authFailures` limiter, and `registerExtraRoutes` for tests.
- `docs/ENGINEERING/05` **rewritten from this real module** (v2), replacing
  the invented placeholder-framework folder example.

## Definition of Done evidence

- **Every route registered after this task requires authentication by
  default (opt-out)** -- `tests/authentication.test.ts`: a route added with
  only a permission is `401` without a key; a route with neither permission
  nor `public` makes `buildApp` throw; `public: true` routes are reachable.
- 401 vs 403 exact; tenant from the key even when a `tenant_id` is in the
  query and a header; body not read before authentication; 503 when the
  store is down (no internal address in the body); limiter blocks with
  `Retry-After` and ignores successes.
- `tests/api-keys-http.int.test.ts` (real DB): create/list/rotate/revoke
  over HTTP; **the cross-tenant 404 on every `:id` route** (get, rotate,
  revoke), both via the foreign and the caller's own application id, with
  the victim key still working afterwards; application confinement;
  escalation refused for issue, rotate, and `all_projects`.
- End to end with the built artifacts: `dist/provision.js` issued a key;
  `dist/server.js` answered 401 without it, 200 list and 201 create with
  it; the server log contained no key material.

## Security findings (fixed here)

1. **Privilege escalation through key management.** Before this task's
   rule, any key holding `api-key:create` could mint a key with any
   permissions, and any key holding `api-key:update` could rotate an admin
   key and receive the new plaintext. Now refused with `403`, tested.
2. **A database outage would have looked like a bad key** (the error
   handler would have answered 500, and a naive mapping 401). Mapped to
   `503`, retryable, tested.

## Deviations from the spec

- The auth-endpoint rate limit is an in-memory per-process floor; the
  Redis-backed limiter is `P5-03`. Blocking is per address, so clients
  behind one NAT share the failure budget (stated in `docs/SECURITY/03`).
- Permission strings are still shape-checked; `P1-04` adds the closed
  vocabulary and role matrix, and user principals.
- `docs/ENGINEERING/05`'s template (promised for `P1-02`) was written here,
  where the routes -- the full slice -- first exist.
