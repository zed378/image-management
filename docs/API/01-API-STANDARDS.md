# 01 - API Standards

> Category: **API Contract** (`docs/API/`) &nbsp;|&nbsp; Status: Final (v1) &nbsp;|&nbsp; Owner: TBD

## Purpose

The conventions every endpoint in the management and admin APIs follows, so
a client that has used one endpoint can predict the shape of every other.
This document is **normative**; `docs/ENGINEERING/06` describes how the code
produces these shapes, and defers to this document where they could differ.

## Category Mandate

The platform is API-first. Every capability exposed to a consumer
application is defined here as a versioned, documented HTTP contract before
it is implemented. SDKs and the dashboard are clients of this contract.

---

## Transport

- HTTPS only in every shared environment. Plain HTTP is local development.
- Request and response bodies are JSON (`application/json; charset=utf-8`),
  except uploads (multipart or a presigned PUT) and image delivery (bytes).
- Error responses are **always** JSON, whatever the request's `Accept`.
- Paths are lowercase, plural nouns, `kebab-case`:
  `/v1/projects/{project_id}/assets`, never `/getAsset`.

## Versioning

Every management and admin route lives under `/v1`
(`04-API-VERSIONING.md`). Probes (`/healthz`, `/readyz`) and the delivery
path (`/i/{asset_id}`, versioned by `docs/IMAGE-DELIVERY-PROTOCOL/30`) do not.

## The envelope

### Success

```json
{
  "data": { "id": "01J8Z3K5M6N7P8Q9R0S1T2V3W4", "content_type": "image/jpeg" },
  "meta": { "request_id": "01M31RYYSHBD056CQBYYNW1C5P" }
}
```

A collection nests an array under `data` and adds pagination to `meta`
(`07-PAGINATION.md`):

```json
{
  "data": [ { "id": "01J8Z3K5M6N7P8Q9R0S1T2V3W4" } ],
  "meta": { "request_id": "01M31...", "next_cursor": "01J8Z3...", "has_more": true }
}
```

### Error

```json
{
  "error": {
    "code": "route_not_found",
    "message": "No route matches this method and path.",
    "details": [],
    "request_id": "01M31RYZDTGHDB78WVH9AQW2GD"
  }
}
```

### Rules

- A success body has `data` and `meta`, never `error`. An error body has
  `error`, never `data`. A client can branch on the presence of one key.
- `data` is never a bare scalar at the top level of the document; it is
  always under `data`, so `meta` can grow without breaking clients.
- `error.code` is stable and machine-readable (`05-ERROR-HANDLING.md`);
  `error.message` is for humans and may change wording at any time.
- `error.details` is always present (possibly empty): a list of
  `{ "field": string?, "reason": string }`.
- `meta.request_id` / `error.request_id` always equal the `X-Request-Id`
  response header.

## Naming and types

| Concern | Rule | Example |
|---|---|---|
| Field names | `snake_case` (`ADR-011`) | `"content_type"`, `"created_at"` |
| Identifiers | ULID strings, 26 characters, uppercase (`ADR-003`) | `"01J8Z3K5M6N7P8Q9R0S1T2V3W4"` |
| Timestamps | RFC 3339, UTC, millisecond precision, `Z` suffix | `"2026-09-21T10:15:54.838Z"` |
| Durations | integer with the unit in the field name | `"ttl_seconds": 3600` |
| Sizes | integer bytes, unit in the name | `"byte_size": 204800` |
| Enumerations | lowercase `snake_case` strings | `"status": "ready"` |
| Booleans | `true`/`false`, positive names | `"is_public": false` |
| Money | integer minor units + ISO 4217 currency | `"amount": 950, "currency": "USD"` |

### `null` versus absent

- `null` -- the field applies and is known to be empty
  (`"deleted_at": null`: not deleted).
- absent -- the field does not apply to this resource or was not requested.

Clients must not treat the two as interchangeable, and the server never
sends a field as `null` merely to "include everything".

## Headers

| Header | Direction | Meaning |
|---|---|---|
| `X-Request-Id` | response | ULID generated by the platform for every request. A client-supplied value is ignored, never trusted as a correlation key |
| `traceparent` | both | W3C Trace Context. Continued when the client sends a valid one; otherwise a new trace is started. Always echoed |
| `Authorization: Bearer <api key>` | request | Authentication (`02-AUTHENTICATION.md`, `P1-03`) |
| `Idempotency-Key` | request | Safe retries of `POST` (`08-IDEMPOTENCY.md`, `P2-02`) |
| `Location` | response | On `201 Created`, the new resource's URL |
| `RateLimit-*`, `Retry-After` | response | Rate limiting (`06-RATE-LIMITING.md`, `P5-03`) |

Quote the `X-Request-Id` in any support request; it retrieves every log line
the request produced.

## Methods and status codes

| Method | Use | Success status |
|---|---|---|
| `GET` | read; never changes state | `200` |
| `POST` | create, or a non-idempotent action | `201` (with `Location`) or `202` for accepted async work |
| `PATCH` | partial update | `200` |
| `PUT` | full replacement (rare) | `200` |
| `DELETE` | delete | `204`, no body |

Error statuses and their codes: `05-ERROR-HANDLING.md`. Two rules worth
stating here because they are security properties:

- A resource owned by another tenant is `404`, byte-identical to one that
  does not exist (`docs/SECURITY/11-IDOR-BOLA-PREVENTION.md`).
- `401` means "who are you?" (no or invalid credential); `403` means "you,
  specifically, may not" (`P1-03`).

## Limits

- JSON request bodies: 1 MiB (`413 payload_too_large` above it). Images are
  never sent as JSON.
- Unknown JSON fields in a request body are rejected (`400`), so a typo is
  never silently ignored.
