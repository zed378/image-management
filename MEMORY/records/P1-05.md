## What was built

- **Step 1** (the query-layer helper) was built early, in `P1-02`:
  `scoped()`, a Kysely plugin that ANDs the tenant/project predicate onto
  the final statement and validates inserts. This task made bypassing it
  *structurally* hard: a new ESLint rule forbids `selectFrom` /
  `updateTable` / `deleteFrom` / `insertInto` on a raw identifier in any
  module repository (only `scoped(...)` chains and `eb.` subqueries), with
  a proof case in `tools/tests/lint-rules.test.ts` for both the violation
  and the allowed form.
- **Step 2**: the isolation harness, `services/api/tests/isolation/`
  (`harness.ts`: tenant fixtures with an all-permission key,
  `runIsolationCase`; `cases.ts`: `ISOLATION_CASES`).
- **Step 3**: `services/api/tests/tenant-isolation.int.test.ts` runs every
  case against the existing endpoints (the five API-key routes).
- Documents made Final: `MULTI-TENANCY/04`, `08`, `SECURITY/10`, `11`.

## Definition of Done evidence

- The harness is a reusable suite in the `integration` CI job, not a
  script. Each case asserts attacker `404` **and** owner `< 400`: the
  owner call prevents a vacuous pass by a route that 404s for everyone.
  The attacker holds every permission, so its 404 can only come from
  isolation.
- `docs/SECURITY/11` names the harness as the enforcement mechanism.
