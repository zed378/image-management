# P0-04: Structured configuration & secrets loading

- **Date:** 2026-09-21
- **Author:** Agent session (Claude Opus 5, Claude Code)
- **Branch / PR:** `feat/P0-04-configuration`, squash-merged to `main`
- **Implements:** `docs/DEVOPS/03-CONFIGURATION.md`, `docs/DEVOPS/04-SECRETS-MANAGEMENT.md`

## What was built

- `packages/config`:
  - `parseConfig(schema, env)` -- validates, returns typed values, or throws
    a `ConfigError` listing **every** problem, by variable name, never value.
  - `withDotEnv(env, path)` -- merges `.env` under the process environment;
    skipped entirely when `NODE_ENV=production`.
  - Shared schema fragments (process, database, redis, storage) with
    `refineStorage` for cross-field rules, and mappers to nested typed
    config objects.
- `services/api/src/config.ts`, `services/worker/src/config.ts` -- each
  deployable's schema, composed from fragments.
- Both `server.ts` entry points load config first and `exit(1)` with the
  error on stderr when it is invalid.

## Deviations from the spec

None in behaviour. The task suggested the hierarchy "process env > `.env`
(local only) > code defaults"; implemented exactly, with one addition: empty
values (`KEY=`) are treated as unset so an empty required secret cannot boot
as `""`.

## Decisions worth recording

- **Schema over flat env names, then mapped to nested config.** Every error
  then names the variable an operator must change.
- **Custom (cross-field) issues are reported before the generic "missing"
  reason** -- found by a failing test: "is required but not set" was masking
  the more useful "is required when STORAGE_PROVIDER=s3".
- **AWS Secrets Manager** named as the secrets manager, with a deliberately
  narrow contract (secrets arrive as env vars before start), so changing
  provider touches manifests only.
- **Config errors print to stderr, not the logger**, because the logger's
  level is itself configuration.

## Tests added

- `packages/config/src/config.test.ts` (16 tests), including the check that
  no secret value appears in any `ConfigError` message.
- `services/api/tests/boot.test.ts` (10 tests) -- spawns the real `api` and
  `worker` entry points with a throwaway `cwd` (so a developer's `.env`
  cannot satisfy the test): each boots with the required variables; each
  exits `1` naming the variable when any one required variable is removed.

## What the next task/session needs to know

- A new variable needs: its fragment or service schema entry, a row in
  `docs/DEVOPS/03-CONFIGURATION.md`, and a line in `.env.example` -- in the
  same change.
- Zod 4 issue shapes differ from Zod 3: enum failures are `invalid_value`
  with a `values` array. `describeIssue` depends on that.
- The boot test runs TypeScript entry points through `tsx`'s ESM loader
  resolved with `import.meta.resolve("tsx/esm")`; it passes `PATH` and
  `SYSTEMROOT` through because Windows child processes need them.
